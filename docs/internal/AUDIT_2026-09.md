# laserfiche-mcp — Deep-Dive Engineering Audit (2026-09-28)

> **Methodology:** independent, fresh 15-dimension review (every `src/` module, architecture, testing, MCP tool-surface UX/DX, security, observability, documentation, and the in-flight uncommitted diff) run via a 268-subagent workflow. Each of the 84 candidate findings was adversarially checked by 3 independent skeptics before being counted as confirmed (83 confirmed, 1 refuted as a false positive; severity split: 27 high, 39 medium, 17 low, 0 critical). This is a separate, independent pass from the earlier three-pass v2.0 audit (`AUDIT.md` / `AUDIT_ERRORS.md` / `AUDIT_DESIGN.md`) — those are historical planning notes and were explicitly excluded as evidence during this review; every finding here was checked against the actual current code.
>
> **Verified test/lint baseline at review time (2026-09-28, working tree with the uncommitted Cloud-auth/destructive-scope diff applied):**
> - `pytest`: 794 passed, 12 skipped, 0 failed — 91.96% branch coverage (gate: 85%)
> - `ruff check src tests`: clean
> - `ruff format --check src tests`: **fails** on `src/laserfiche_mcp/auth.py` (1 file needs reformatting — also called out as a low-severity finding below)
> - `mypy`: clean across 50 source files (`disallow_untyped_defs`, `check_untyped_defs`, `warn_return_any`)

## Executive summary

laserfiche-mcp v2.3.0 is a well-architected, carefully-reasoned MCP server — the client → ops → tools layering is real and consistently applied, the confirmation-token destructive-safety design is genuinely best-in-class, and `ruff`/`mypy` are clean across the codebase. It does **not** yet clear the bar this audit was asked to hold it to ("no bugs, no ugly interfaces, state of the art"): 23 P0-severity defects survived independent adversarial verification, several of them (the FastMCP onboarding `instructions` pointing at unregistered tools, the CLI's `--help`/`--version` crashing on the project's own documented invocation pattern, three unguarded crash points in the new Cloud-auth and file-I/O paths, an OData-injection-shaped quote-escaping gap, and an allowlist that silently breaks the very "recommended" wrapper tools the docs tell operators to allowlist) are exactly the class of concrete, reproducible, user-facing bug the "production grade" bar rules out. The single biggest risk is the freshly-added Cloud/API-key auth path: `CloudServiceAppStrategy._build_assertion_jwt()` is unguarded and will raise a raw, misleadingly-labeled exception on the very first malformed-key or missing-`pyjwt[crypto]` case — independently flagged by three different area reviews, which is strong convergent evidence it's real. The single biggest strength is the error-contract/confirmation-token design (`errors.py`, `confirmation.py`, `permissions.py`): HMAC-signed, TTL-bound, per-parameter-hash-bound tokens with fail-closed defaults are genuinely textbook, and most of the codebase (client layer, ops layer, read tools, core write tools) honors that contract with real discipline. This is a strong v2.3.0 with a clear, short, well-scoped punch list standing between it and "state of the art" — not a rewrite.

## Findings by priority

### P0 — critical/high (fix before calling this production-grade)

- **`src/laserfiche_mcp/_app.py:60`** — The FastMCP `instructions` string shown to every client at session start names six legacy (v1.x) tool identifiers, none of which are registered under the v2.3.0 default (`LF_LEGACY_TOOL_NAMES` unset → false). *Scenario*: a fresh default install's own onboarding text tells the model to call `search_content`/`get_entry`/etc., all of which return unknown-tool errors on the first try. *Fix*: generate `instructions` from the registry's current v2 names (or `v2_rename_map()`) so it can't drift from what's actually registered.

- **`README.md:453`** (also 477) — README's canonical Tools table, which `getting-started.md` and `error-contract.md` both point readers to as authoritative, documents only 34 of the 51 currently-registered tools (33% missing), including two tools (`compare_entries`, `find_duplicate_documents`) absent from the file entirely. *Scenario*: an operator scoping `LF_WRITE_TOOLS_ALLOWED` from this table unknowingly blocks a third of the write surface. *Fix*: regenerate the table from `all_tools()`, ideally with a CI check that fails on drift.

- **`docs/error-contract.md:92`** — The "Tool-specific pre-server errors" table, billed as the comprehensive taxonomy, is missing at least 7 real subkinds actually emitted by shipped code: `destructive_scope_required`, `preview_does_not_accept_token`, `execute_requires_token`, `conflicting_modes`, `fields_ignored_on_remove`, `invalid_mode`, `no_op`, plus `async_search_unavailable`/`search_timeout`/`search_failed` (also absent from `errors.py`'s own `_SUBKIND_TO_KIND` map — see below). *Fix*: add the rows, or generate this table from `_SUBKIND_TO_KIND` plus a registry of local-guard slugs so it can't silently drift again.

- **`smithery.yaml:21`** — Hard-locks `LF_DEPLOYMENT_MODE` to `enum: [self_hosted]` ("Cloud is reserved for v2") and `LF_AUTH_MODE` to `enum: [password, oauth]`, with no fields for `LF_CLOUD_ACCESS_KEY`/`LF_CLOUD_SERVICE_PRINCIPAL_KEY`. *Scenario*: a Smithery-driven install cannot reach the Cloud (BETA) auth path the rest of the project documents as available — the schema structurally forbids it. *Fix*: add `cloud`/`api_key` to the enums and the two Cloud secret fields, matching `.env.example`.

- **`src/laserfiche_mcp/auth.py:315`** (same root cause independently confirmed at lines 319, 332, 334 across three separate area reviews) — `CloudServiceAppStrategy._build_assertion_jwt()` has zero error handling around JWK/JWT construction, so a malformed/incomplete `LF_CLOUD_ACCESS_KEY` or a missing `pyjwt[crypto]` install (undocumented dependency — see `oauth.py:41` below) raises a raw, uncaught exception on every tool call, bypassing the `LaserficheError` contract this same module explicitly refactored `_post_token` to guarantee. *Fix*: wrap `_build_assertion_jwt()` (or its call site in `_refresh()`) in try/except, re-raise as `LaserficheError`; validate `jwk`'s `crv`/`x`/`y`/`d` fields eagerly in `_decode_cloud_access_key` so this fails at startup as the docstring already claims.

- **`src/laserfiche_mcp/oauth.py:41`** — Cloud auth (`LF_AUTH_MODE=api_key`) has a hard runtime dependency on `pyjwt[crypto]`, which ships only in the `oauth`/`dev` extras — undocumented everywhere Cloud setup is described, and the resulting error message (`_INSTALL_HINT`) blames the unrelated `--http` OAuth Resource Server feature. *Fix*: add `pyjwt[crypto]` as a base dependency, or document the extra in `.env.example`'s Cloud section and give `CloudServiceAppStrategy` its own install-hint message.

- **`src/laserfiche_mcp/cli.py:304`** — `-h/--help` and `-V/--version` are plain `store_true` flags checked only after parsing succeeds, so combining either with any repository subcommand (all of which have a required positional) crashes with an argparse usage error instead of showing help. *Reproduced*: `laserfiche-mcp --help ls` exits 2 with `laserfiche-mcp ls: error: the following arguments are required: folder`. *Fix*: register `-h/--help`/`-V/--version` as real argparse actions or short-circuit before `parser.parse_args`.

- **`src/laserfiche_mcp/errors.py:71`** — `_SUBKIND_TO_KIND` is missing `not_a_folder`, `source_path_not_allowed`, and `child_count_probe_failed`, so `kind_for_subkind()`'s fallback mislabels them as `upstream_unavailable`. *Scenario*: `import_document` against a disallowed local path returns `{"error":"source_path_not_allowed","kind":"upstream_unavailable",...}` — a permission/config problem mislabeled as a server outage, so an agent branching on `kind` (the documented public contract) treats it as retryable when it isn't. Confirmed untested: existing tests assert `error` but never `kind`. *Fix*: add `"not_a_folder": "invalid_input"`, `"source_path_not_allowed": "permission_denied"`, `"child_count_probe_failed": "upstream_unavailable"`.

- **`src/laserfiche_mcp/models.py:59`** — `EntrySummary`/`EntryDetail`/`SearchResults.from_api()` raise an uncaught `pydantic.ValidationError` (not `LaserficheError`) on a blank/unparseable `creationTime`/`lastModifiedTime`. *Reproduced*: `EntrySummary.from_api({'id':1,'name':'x','entryType':'Document','creationTime':''})` raises directly. Every read tool (`search_entries`, `list_folder`, `get_entry`, `search_natural`, etc.) is exposed; `tool_logger`'s generic exception handler logs and *re-raises*, so this escapes as a raw unstructured failure, contradicting the module's own stated purpose. *Fix*: make `from_api()` tolerant of malformed timestamps (swallow-and-return-`None` field validator), add a regression test with an empty-string date.

- **`src/laserfiche_mcp/ops/content_search.py:60`** (also flagged independently at line 61) — `build_search_command()` escapes `"` in the search phrase but not in `folder_path` before interpolating both into the Laserfiche search grammar. *Reproduced*: `build_search_command('lease terms', 'Q1 "Draft" Folder')` produces a broken/widened `{LF:LookIn=...}` clause. The sibling tool `search_by_name` (`tools/reads.py:127-131`) gets this right. *Fix*: `folder_path.replace('"', '\\"')` before interpolation, mirroring `reads.py`; add a test mirroring the existing quote-escaping test but for `folder_path`.

- **`src/laserfiche_mcp/ops/extract.py:237`** — `_extract_docx`/`_extract_pptx` only guard `zipfile.BadZipFile` at the initial `ZipFile(path)` open; a structurally valid zip with a corrupted member raises a raw, uncaught `BadZipFile` from `archive.read()`, bypassing the documented `ExtractionError` contract. *Fix*: wrap `archive.read()` itself in try/except and raise `ExtractionError("malformed_docx"/"malformed_pptx", ...)`.

- **`src/laserfiche_mcp/ops/extract.py:326`** — `_extract_eml` has no exception handling around message parsing/body decoding; an EML with an unrecognized charset raises a raw `LookupError` instead of `ExtractionError`. *Fix*: wrap the body of `_extract_eml` in a broad try/except raising `ExtractionError("malformed_eml", ...)`.

- **`src/laserfiche_mcp/ops/manifest.py:151`** — `walk()`'s `max_entries` cap is checked only after a folder's entire child listing has already been paged through in full. *Reproduced*: `walk(repo, root, max_entries=10, page_size=50)` against a 5,000-child folder still issues 101 requests before truncating to 10 rows — directly contradicting the docstring's "stop, not a filter" cost claim. *Fix*: thread the remaining budget into `_list_all_children` so paging for one folder stops as soon as the budget is exhausted.

- **`src/laserfiche_mcp/ops/pages.py:38`** — `parse_page_spec` has no upper bound on requested page-range size and runs synchronously inside `async def get_document_edoc` (`tools/documents.py:619`) with no executor offload. *Reproduced*: `parse_page_spec("1-5000000")` takes 2.3s and materializes 5M entries; a caller-typo'd spec like `"1-999999999"` would take minutes/GBs while blocking the single-threaded event loop for every other concurrent request. *Fix*: reject/cap expanded range size before calling `range()`/`.update()`, matching `max_matches` bounds used elsewhere.

- **`src/laserfiche_mcp/search.py:112`** — `repair_escape_quotes`'s hand-rolled state machine misreads a value ending in a single backslash immediately before its closing quote as an already-escaped quote, corrupting later, unrelated clauses. *Reproduced twice*: (1) a genuinely-malformed query is "repaired" into a still-malformed one (wasting one of `search_natural`'s 3 repair attempts); (2) an already-valid query is needlessly mutated (`changed=True` on a query that never needed repair). *Fix*: reuse the same closing-quote lookahead the bare-quote branch already uses before deciding a `\"` is an escape vs. the value's real terminator.

- **`src/laserfiche_mcp/tools/_helpers.py:153`** — `LF_WRITE_TOOLS_ALLOWED` breaks every wrapper/collapsed/split write tool when an operator allowlists only the wrapper's own name, because the delegate's internal `check_write_permission` call uses the *underlying* tool's hardcoded name, not the invoked tool's name. *Reproduced live* for both `field_update`→`merge_fields` and `rename_entry_preview`→`rename_entry`: allowlisting exactly the tool the module docstring recommends still fails with `tool_not_allowed`. Same pattern affects `tag_update`, `link_update` (mode='replace'), `template_assign_or_remove`, and all 10 preview/execute split tools. Zero test coverage of `LF_WRITE_TOOLS_ALLOWED` exists for either collapse or split families. *Fix*: make `check_write_permission`'s allowlist check consider the full name-family (wrapper + delegate names), or document the requirement and add a regression test.

- **`src/laserfiche_mcp/tools/_validators.py:260`** — `validate_required_fields` only parses the v2 camelCase field-value shape (`current.get("value")`, `fv.get("fieldName")`), with no v1 PascalCase fallback — while `LF_API_VERSION` defaults to v1. *Scenario*: on a default (v1) server, `already_set` is always empty, so `assign_template`'s preflight reports every required field as missing even when already set — reintroducing the exact "preflight over-aggression" failure class the maintainer already knows about, via an untested code path (existing tests only use camelCase fixtures). *Fix*: mirror the fallback used elsewhere in this codebase (`_helpers.py:251-254`): `current.get("value") or current.get("Value") or []`.

- **`src/laserfiche_mcp/tools/content_search.py:44`** (root-cause overlap with line 35) — `_classify_create_error` overwrites `error` to `"async_search_unavailable"` on a 404 but leaves `kind` at `"not_found"` — a self-contradictory envelope — *and* is applied to every `LaserficheError` escaping `run_search`, not just create-time failures, so a later-stage 404 (e.g., a mid-flight token-expiry race) gets the same "this build has no async search" misdiagnosis. Existing test asserts `error`/`hint` but never `kind`. *Fix*: set `kind="upstream_unavailable"` alongside the override (or add the three async-search subkinds to `_SUBKIND_TO_KIND`), and scope the relabeling to `create_search` failures specifically.

- **`src/laserfiche_mcp/tools/duplicates.py:157`** — `find_duplicate_documents` has no exception handling around `manifest.walk`/`duplicates.find_duplicates`, and the local disk I/O they trigger (`_request_stream_to_file`'s `mkdir`/`open('wb')`/`write`) is unguarded against `OSError`/`PermissionError` — very reachable on Windows (the project's own dev platform) via AV locks or a full/locked temp dir. *Fix*: wrap the export call in `ops/duplicates.py`'s hash loop in `except (LaserficheError, OSError)`, routing `OSError` into `report.skipped`.

- **`src/laserfiche_mcp/tools/natural_search.py:50`** — `_sample_folder_templates` reads raw `list_folder`/`get_entry_by_path` payloads with single-case key lookups (`folder.get('id')`, `children.get('value')`) instead of the camelCase/PascalCase dual handling every sibling consumer of this exact payload shape uses (`models.py`'s `_pick`, `manifest.py`, `client/_search.py`). *Scenario*: on a self-hosted v1 server (this project's actual deployment target, per its own test fixtures confirming v1 returns `Id`/`Value`), Mode A template auto-discovery is completely and silently broken — `folder_path` is discarded, the fallback root also returns no children, and the tool emits misleading diagnostic notes about *why*. *Fix*: route through the existing dual-case helpers instead of bespoke `.get('id')`/`.get('value')`.

- **`src/laserfiche_mcp/tools/natural_search.py:221`** — `search_natural`'s Mode B failure responses don't carry the documented "stable across releases" envelope (no `kind`/`error`/`request_id`), and the documented `bad_query_syntax` subkind is never actually emitted anywhere in source (grep-confirmed). *Fix*: add `kind`/`error`/`operation`/`request_id` to the error dumps in `_run_execute_mode`, or update `error-contract.md` to describe the actual bespoke shape and remove the orphaned `bad_query_syntax` row.

- **`src/laserfiche_mcp/tools/writes_create_copy_import.py:235`** — `_read_import_file()` checks `isfile()`/`getsize()` but the actual `open(file_path,'rb').read()` is unguarded. *Scenario*: on Windows, a file open in another app (Word/Adobe/Excel) routinely passes `isfile()` but raises `PermissionError` on open — a routine user mistake on `import_document`, one of the most commonly used write tools — leaking a raw exception instead of the documented structured error. *Fix*: wrap in try/except `OSError`, return `local_error('import_document', 'file_read_failed', ...)`.

- **`src/laserfiche_mcp/tools/writes_move_rename.py:277`** (also 280) — `move_entry` hand-rolls its destination-folder fetch instead of using the shared `check_write_for_parent` helper, and **silently skips the destination path-fence check** if that fetch raises `LaserficheError` for *any* reason (429/5xx/timeout), not only a genuine 404. This is asymmetric with the source side, which fails closed via `fetch_entry_for_op`/`ToolAbortedError` on the identical error class, and directly contradicts the tool's own docstring claim that "the path fence checks BOTH source and destination." The one existing test only covers a genuine 404 (where fail-open is harmless); it does not distinguish that from a transient error against a real, denied destination. *Fix*: route through `check_write_for_parent("move_entry", new_parent_id)` so a fetch failure raises and surfaces a structured error instead of silently proceeding unfenced.

## Architecture & modularity

The client → ops → tools layering is real, not aspirational: `client/` never imports `tools`/`ops`; `ops/` depends on the concrete client only through narrow Protocols or an injected `client: Any`, letting `content_search`, `duplicates`, `manifest`, and `compare` compute be reused verbatim by both MCP tools and `cli_commands.py`. No circular imports exist at runtime (verified both import orders), and the two places a cycle would otherwise exist (cli↔server↔http_transport) are broken with deliberate, commented lazy imports. The `ToolSpec`/`@register` registry (`tools/_registry.py`) is a genuinely good pattern — one decorator replaces three previously hand-maintained lists — and `server.py`'s two-phase register-then-apply design is correctly wired end to end. The real architectural wart is catalog redundancy, not layering: by default, the server registers up to three overlapping v2-named tools per conceptual write action (`server.py:116`), and `cli.py`'s 898 lines bundle four separable concerns (arg parsing, diagnose probing, the setup wizard, orchestration) that would fit the same `client/`-style mixin split the rest of the codebase already uses elsewhere.

## Testing & quality gates

The test suite (14,268 test lines vs. 13,648 source lines; ~794 collected cases) is proportionate and scenario-dense, not padded — encrypted/malformed PDF fixtures, Windows-hostile filenames, real RSA-signed JWTs (no mocked crypto) in `test_oauth.py`, and three reproduced confirmation-token "drift attack" regressions with explicit "nothing reached the DELETE endpoint" assertions. Time-based logic is consistently tested via monkeypatched clocks, avoiding flakiness on that axis. `ruff check`/`ruff format --check` and `mypy --strict`-ish are part of the baseline gate; `ruff format --check` currently fails on one isolated block in the in-flight `auth.py` diff (`auth.py:259`). The gaps are narrow but real: `LF_WRITE_TOOLS_ALLOWED` has zero test coverage against the collapse/split tool families — exactly the surface where `tools/_helpers.py:153`'s access-control break lives, so it shipped silently; two test files share a structurally-dead conditional that would mask a real response-contract regression (`test_writes_delete_edoc_pages.py:263`); `test_http_transport.py:150` has order-dependent cleanup that only runs after assertions; and property-based testing for the two parser-like layers (`search.py`, `permissions.py`) remains absent, as `TODO.md` already tracks. Per the harness's constraint, this report does not claim a pytest pass/fail verdict — that result is appended separately by whoever ran the coverage-gated suite.

## MCP tool-surface UX/DX (the interface an LLM and a human both read)

Parameter-level UX is unusually disciplined: every parameter across ~50 tool functions carries a live `Field(description=...)`, naming holds to `laserfiche_{resource}_{verb}` almost everywhere, and error messages consistently name the next call to make. Where it falls short of "state of the art" is consistency in the newest additions: `server.py:116` registers three same-purpose tools per destructive operation with no cross-referencing docstrings to say which to prefer (`writes_fields_tags_links.py:56`); paired tools that docstrings explicitly link to each other return incompatible success shapes with no discriminator key (`writes_fields_tags_links.py:94` — `set_fields` vs. `merge_fields`, `list_field_definitions` vs. `get_template_fields`); and the one tool whose name breaks the catalog's own naming convention, `task_wait_or_poll` registered as `laserfiche_task_update` despite being a pure read (`write_collapses.py:408`), is exactly the kind of "docstring/name an LLM would misread" defect this audit was asked to find. Underneath the polish, `LF_WRITE_TOOLS_ALLOWED` — the primary operator-facing safety control for scoping the write surface — silently breaks every collapsed/split "recommended" tool the module docstrings tell operators to allowlist (`tools/_helpers.py:153`), which is a DX failure with real safety consequences, not just a cosmetic one.

## Security & destructive-action safety

This is the strongest area of the codebase, and the confirmed findings largely reinforce that rather than undercut it: `confirmation.py`'s HMAC token design (constant-time comparison, per-parameter hash binding, 5-minute expiry) is textbook and verified concretely for `rename_entry`, `move_entry`, and `delete_pages`; `permissions.py`'s path fence gets prefix-boundary matching and unconditional `..`-rejection right; `oauth.py` restricts to asymmetric algorithms only and fails closed on any exception; and `check_destructive_scope` fails closed when scopes are absent. The real gaps cluster at the edges of this design rather than its core: `move_entry` is the one place a shared-infra bypass has genuine security relevance — it hand-rolls its destination fetch and fails *open* (skips the path fence) on any lookup error rather than failing closed like the identical source-side check (`writes_move_rename.py:277/280`); the freshest code (Cloud/API-key auth) doesn't get the same "never let a raw exception escape" discipline as the rest of `auth.py` (`auth.py:315` et al.); and one dynamically-built search path skips the quote-escaping its sibling correctly applies, letting an attacker-controlled `folder_path` widen or break a search's scope (`ops/content_search.py:60`). None of these are externally exploitable in the classic sense — Laserfiche's own server-side ACLs are the real backstop — but they are honest, fixable bugs in fences whose entire purpose is defense-in-depth for an agent-driven write surface.

## Observability & error-handling consistency

The error-contract core (`classify_lf_error`/`local_error`/`invalid_token_response`) is applied with near-total consistency across ~35+ error-construction call sites, `request_id` and `upstream_trace_id` are threaded through nearly everywhere, and `LF_LOG_FORMAT=json` is fully wired end to end, not aspirational. The regression is that "raw exceptions leaking to the MCP client" — the exact failure class the structured contract was built to eliminate — has crept back in through several non-HTTP paths that fall outside `LaserficheError`: the Cloud auth JWT path (`auth.py:315`), local disk I/O in `find_duplicate_documents` and `import_document` (`duplicates.py:157`, `writes_create_copy_import.py:235`), a success-path `response.json()` in `_request_json` (`client/_core.py:194`), and pydantic validation of malformed API timestamps (`models.py:59`) — each independently verified via the MCP SDK's own lowlevel server, which reduces any uncaught exception to a bare `isError:true / str(e)` with no `request_id`/`kind`/slug. Secondary but real: `errors.py`'s subkind→kind map has gaps that self-contradict responses (`errors.py:71`), one classifier is applied more broadly than its documented trigger (`content_search.py:44`), and log-severity is undifferentiated by `kind` so routine `not_found` results and genuine outages are equally loud at WARNING (`observability.py:298`).

## Documentation & onboarding

Prose-level writing is genuinely strong and honest — the CHANGELOG self-corrects a previously-published claim rather than quietly editing it, and `docs/error-contract.md`/`docs/data-handling.md` read as real technical writing. The structural problem is catalog staleness, and it's severe at the reference-doc level: the README's own stated single source of truth for "what tools exist" documents two-thirds of the write surface a `LF_READ_ONLY=false` deployment actually exposes (34 of 51 tools, verified by diffing `@register` decorators against the README text — `README.md:453`), the error-contract's subkind table has the same blind spot for the same newly-shipped tools (`docs/error-contract.md:92`), and `smithery.yaml` has independent drift that structurally blocks the documented Cloud auth path and advertises the wrong default for `LF_LEGACY_TOOL_NAMES` (`smithery.yaml:21`, `:108`). ## What's already state-of-the-art here

- **Confirmation-token destructive-safety design** (`confirmation.py`): HMAC-SHA256 with a domain-separated KDF label, `hmac.compare_digest`, exact per-parameter hash binding so a preview for one set of arguments provably can't be replayed against different ones — verified concretely for `rename_entry`'s `new_name`, `move_entry`'s `new_parent_id`/`new_name`, and `delete_pages`' `page_range`+`page_count`, with three reproduced "drift attack" regression tests (`test_token_param_binding.py`) asserting nothing reached the DELETE endpoint.
- **Structured, near-universally-applied error contract** (`errors.py`, `docs/error-contract.md`): `request_id`/`upstream_trace_id` threaded through ~35+ error-construction sites; 9010/9528 credential-error special-casing correctly implemented and tested; the design itself (not its current table-drift) is sound and well-reasoned.
- **client → ops → tools layering** with zero runtime circular imports, narrow Protocol-typed injection points in `ops/duplicates.py` and `ops/manifest.py`, and genuine client/CLI code sharing through the ops layer rather than duplicated logic.
- **OAuth Resource Server hardening** (`oauth.py`): asymmetric-algorithm-only enforcement (blocks `alg=none`/HS256 confusion both at config-validation time and by construction), trailing-slash-tolerant issuer check, fail-closed on any verification exception.
- **Two-pass duplicate detection** (`ops/duplicates.py`): size-then-hash design correctly handles unique-size skip, unknown-Content-Length documents, oversized-document skip-with-reason, and guaranteed scratch-file cleanup — thoroughly tested against exactly these cases.
- **Config-loading precedence and CLI/MCP code sharing**: env > `--config` > `./.env` > `~/.laserfiche-mcp/.env` correctly implemented via `argparse.SUPPRESS` + `dotenv override=False`, exactly as documented; the same `ops/*` modules power both surfaces, not aspirationally.
- **Clean baseline**: `ruff check` clean, `mypy` clean across 50 source files under `disallow_untyped_defs`/`check_untyped_defs`/`warn_return_any`, and a test suite proportionate to and denser than its source (14,268 vs. 13,648 lines) with real adversarial fixtures (encrypted PDFs, Windows-hostile filenames, in-test-built OOXML, real RSA JWTs).
